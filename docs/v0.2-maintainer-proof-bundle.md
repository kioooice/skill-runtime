# v0.2 Maintainer Proof Bundle

Date: 2026-05-06

## What This Proof Bundle Demonstrates

This proof bundle gives an external reader one narrow, reproducible maintainer-facing path that shows the real v0.2 product story:

- a maintainer workflow can be captured as an auditable record
- the runtime can emit an explicit governed follow-up recommendation
- the operator can see that recommendation in human-readable form
- the JSON audit payload remains intact
- no distill, promote, or apply step runs automatically

This is deliberately not a dashboard proof and not a generic local script demo.

## Maintainer Scenario Used

Scenario:

- `maintainer_review_cleanup`

Input:

- `demo/maintainer_review_cleanup/observed_task.json`

This is the right proof scenario because it is maintainer-facing, recommendation-bearing, and already accepted as a narrow governed follow-up path without claiming that review cleanup is an active workflow-search skill.

## Exact Command Path

Accepted command path:

```powershell
python -m skill_runtime.cli --root ./.tmp_v0_2_proof_bundle capture-trajectory --file demo/maintainer_review_cleanup/observed_task.json --task-id v0_2_proof_bundle --session-id v0_2_proof_bundle --render-recommendation text
```

Reproducible bundle helper:

```powershell
python scripts/run_v0_2_proof_bundle.py
```

The helper only wraps the accepted command path above. It saves the resulting artifacts and prints a summary JSON. It does not call `RuntimeService` directly, does not execute `recommended_host_operation`, and does not invent a second flow.

## What Is Intentionally Not Automated

This proof bundle intentionally does not automate:

- `distill_trajectory`
- `promote_skill`
- `apply_evolution_candidate`
- any dashboard-side follow-up

The recommendation is surfaced, not executed.

## How This Differs From Utility Scripts

This bundle is not proving that the repository can run a local file transform.

It is proving a governed maintainer workflow slice:

- the input is a maintainer workflow observation
- the output is a governed follow-up recommendation
- the recommendation stays auditable in JSON
- the operator-facing text stays explicit about non-automatic boundaries

That is different from a utility script library, where the story would end at “the command produced the file.”

## Why This Does Not Justify Widening `default-in`

This proof bundle demonstrates one accepted maintainer-facing governed follow-up path.

It does not prove:

- broader runtime-entry safety
- broader maintainer workflow coverage
- review cleanup as an active workflow-search skill
- governed learning follow-up as an ordinary active skill
- any reason to widen `default-in`
