# v0.1.0-alpha Release Plan

Date: 2026-05-05

## Release Goal

Ship `v0.1.0-alpha` as a credible early open-source release for local maintainer workflow governance.

Release note source:

- [CHANGELOG.md](../CHANGELOG.md)

The goal is not to claim broad adoption or full product maturity. The goal is to let a reviewer or maintainer:

- understand what Skill Runtime is for
- run a small local verification set
- reproduce one realistic maintainer demo
- see why the runtime is useful without mistaking it for silent autonomous maintenance

## What Is Included

`v0.1.0-alpha` should include:

- the current local-first runtime service, CLI, and MCP surfaces
- governed lifecycle steps for search, execute, capture, distill, audit, promote, and reuse
- maintainer-facing demos, with review cleanup as the main public walkthrough
- architecture and runtime contract verification scripts
- the fast runtime test suite as the main release verification baseline
- documentation that explains product boundary, demo path, and current limitations

## What Is Intentionally Not Included

`v0.1.0-alpha` should not claim or include:

- broad autonomous maintainer operation
- wider `default-in` entry policy
- dashboard-led product positioning
- strong public traction claims
- production-grade hosted service guarantees
- full remote-provider maturity as a release requirement

There is currently no evidence supporting a broader `default-in` policy, so `v0.1.0-alpha` should state that clearly instead of implying imminent expansion.

## Verification Commands

Run these commands from the repository root before tagging or announcing `v0.1.0-alpha`:

```bash
python -m pip install -e .
python scripts/check_mcp_architecture.py
python scripts/check_runtime_contracts.py
python -m unittest tests.test_runtime_fast -v
git diff --check
```

If the release is about to be tagged or announced more broadly, also run:

```bash
python -m unittest tests.test_runtime -v
```

## Demo Path

The main public demo path for `v0.1.0-alpha` is:

1. Read [Main Demo Walkthrough](./main-demo-walkthrough.md)
2. Inspect `demo/maintainer_review_cleanup/expected_cleanup_plan.md`
3. Run the review cleanup `codex-run` boundary check
4. Run `capture-trajectory` on the same workflow
5. Inspect `recommended_next_action` and `recommended_host_operation`

This path is the best public fit for `v0.1.0-alpha` because it shows:

- a realistic maintainer problem
- a concrete follow-up recommendation
- governed learning after successful work
- a clear reason the runtime should remain conservative

## Known Limitations

Current `v0.1.0-alpha` limits should stay explicit:

- semantic audit is provider-backed but mock-backed by default
- fallback distillation is still mock-backed by default
- retrieval is still lightweight
- the runtime is strongest on local file and maintainer workflow patterns
- public traction is still weak and should not be overstated
- there is no evidence yet that review cleanup or similar open-ended work should move into `default-in`

## Next Milestones

After `v0.1.0-alpha`, the next milestones should be:

1. harden the maintainer demo set and keep fresh-clone reproduction clean
2. improve provider-backed audit and distillation quality without changing the current safety boundary
3. gather stronger evidence on where governed reuse helps and where it should remain explicit
4. revisit runtime entry policy only after new evidence, not by assumption

Until that evidence exists, there is no basis for expanding `default-in`.
