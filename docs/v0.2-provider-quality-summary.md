# v0.2 Provider Quality Summary

Date: 2026-05-05

## Completed Capabilities

- Added a single local evaluation entrypoint at `scripts/evaluate_provider_quality.py`.
- Kept the evaluation local-first by using demo, mock, and fake DeepSeek fixtures instead of requiring a real provider API key.
- Standardized fixture output around lifecycle visibility:
  - `lifecycle_mode`
  - `generated_candidate_status`
  - `audit_status`
  - `repair_attempted`
  - `repair_status`
  - `execution_smoke_status`
  - terminal `loop_stage`
  - `failure_reason`
  - `recommended_next_action`
- Added formal-vs-manual diagnostics to each fixture report:
  - `staging_file`
  - `generated_candidate_provider`
  - `inferred_or_used_input_schema`
  - `declared_input_schema_keys`
  - `execution_arg_keys`
  - `candidate_kwargs_keys`
  - `schema_execution_arg_mismatch`
  - `expected_artifacts`
  - `produced_artifacts`
  - `missing_artifacts`
- Added a machine-readable baseline at `docs/provider-quality-baseline.json`.
- Added baseline comparison support with `--baseline` and regression-gated exit behavior with `--fail-on-regression`.

## Fidelity Issues Found And Fixed

- Fixed an over-permissive deterministic rule boundary:
  `single_file_copy` could swallow copy-plus-sidecar workflows before fallback distillation had a chance to preserve the metadata step.
- Fixed fallback schema fidelity for the formal runtime lifecycle:
  fallback-generated candidates could read kwargs that did not match the pre-fallback declared input schema.
- Narrowed the repair to metadata alignment only:
  the fallback path now extracts simple `kwargs.get(...)` keys from the generated candidate and rewrites staged metadata `input_schema` to match those keys, recording `schema_source: "fallback_candidate_kwargs"`.
- Added regression coverage for:
  - pure copy still matching the deterministic rule
  - copy-plus-sidecar no longer being swallowed by that rule
  - fallback schema alignment staying consistent with execution args and candidate kwargs
  - baseline comparison matching the current expected fixture set

## Remaining Known Gaps

- Mock-backed fallback and semantic review remain quality-limited by design.
- The review-cleanup maintainer workflow is only partially solved:
  the controlled demo provider can pass, but the open-ended mock-backed version still fails as expected.
- Local demo providers prove hook integration and governed-learning loop behavior, not broad automatic skill generation quality.
- Fake DeepSeek fixtures prove repair and failure visibility, not long-running real-provider stability.
- Provider quality is still being measured on a fixed local fixture set, not on broad real-world maintainer task distributions.

## Why This Does Not Justify Widening Default-In

- Provider quality measures governed-learning quality after task completion, not task-entry safety.
- `default-in` is still a workflow-boundary and risk-policy question.
- Open-ended maintainer judgment tasks such as review cleanup still need conservative handling even when a constrained positive control exists.
- The current evidence only shows that the provider loop can be measured honestly and compared against a fixed baseline.

There is still no evidence here that supports widening `default-in`.

## Recommended Next Core Slice

The next core slice should stay inside provider fidelity, not product-boundary expansion:

- improve provider quality on the existing fixture set
- reduce remaining gap between constrained positive controls and expected-failure maintainer fixtures
- keep the work focused on generation, audit, repair, and execution fidelity within the current governed-learning path

That means no new dashboard work, no wider `default-in`, no automatic promotion, and no automatic application of evolution candidates.
