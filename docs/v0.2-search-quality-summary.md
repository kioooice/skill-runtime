# v0.2 Search Quality Summary

Date: 2026-05-05

## Completed Capabilities

- Added a local search-quality evaluator at `scripts/evaluate_search_quality.py`.
- Kept evaluation local-first:
  it runs in a temporary runtime root and imports a small fixed active-skill fixture set instead of depending on the real working runtime state.
- Standardized the search-quality report around:
  - `query_id`
  - `query`
  - `query_type`
  - `expected_top_skill`
  - `actual_top_skill`
  - `actual_recommended_skill`
  - `matched`
  - `failure_reason`
  - rank diagnostics and top results
- Added minimal metadata-driven alias recall through `search_aliases`.
- Added a machine-readable baseline at `docs/search-quality-baseline.json`.
- Added baseline comparison support with `--baseline` and regression-gated exit behavior with `--fail-on-regression`.

## Search Limitations Found

- Search is still local and lexical.
- Tokenization still centers on ASCII-style alphanumeric tokens and underscores.
- There is no embedding, external search service, or LLM retrieval.
- There is no general Chinese tokenization or semantic retrieval.
- A result may appear in `top_k` without being recommended if it stays below the runtime recommendation threshold.

## Alias-Based Recall Improvement

- Added optional `search_aliases` to skill metadata.
- Wired aliases into local searchable text and lightweight scoring without changing the larger ranking structure.
- Used `merge_text_files` as the first narrow recall improvement target.
- Chinese support is still explicit-alias only:
  it supports known declared aliases such as `把多个文本文件合并成一个文档`, not general Chinese understanding.

## What This Proves

- Local retrieval behavior is now reproducible and machine-comparable.
- Known search drift can now be detected without changing the retrieval algorithm first.
- Explicit metadata aliases can improve recall for a known Chinese intent.
- Negative queries can be kept in the baseline so false recommendations stay visible.

## What This Does Not Prove

- It does not prove semantic retrieval quality.
- It does not prove general multilingual understanding.
- It does not prove that the current lexical ranking is broadly sufficient outside the fixed query set.
- It does not prove that silent reuse policy should widen.
- It does not prove that maintainer judgment workflows are safe for broader automatic entry.

## Why This Does Not Justify Widening Default-In

- Search quality is a retrieval and reuse-quality measurement problem, not a runtime-entry safety decision.
- A stable search baseline only shows that current local retrieval behavior is measurable and can be regression-checked.
- It does not answer whether a task should automatically enter the runtime lane.
- It does not change the conservative boundary around maintainer-facing workflows.

There is still no evidence here that supports widening `default-in`.

## Recommended Next Core Slice

The next core slice should stay inside search and reuse quality, not boundary expansion:

- review current ranking diagnostics and false-neighbor behavior inside the existing query set
- identify whether the next useful move is metadata quality, ranking-weight tuning, or a broader but still local fixture/query baseline
- keep the work local, lexical, and explainable

That means no dashboard expansion, no embedding path, no external retrieval service, and no wider `default-in`.
