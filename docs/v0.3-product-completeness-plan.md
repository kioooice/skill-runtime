# v0.3 Product Completeness Plan

## Why Pause Release And Tag Work

`v0.2.0rc1` already proved a narrow release candidate claim: the repository can show governed maintainer-workflow capture, explicit follow-up recommendation, and stable quality gates without widening automation boundaries. That was enough for release-readiness evidence, but it is not the same thing as day-to-day product completeness.

Continuing to optimize tags, release notes, or proof-only packaging would mostly improve presentation. The current higher-value gap is operator usability: a maintainer still needs a faster way to see what the runtime currently knows, what it has captured, and what it can safely do next.

## What v0.2 Already Proved

v0.2 proved these points:

- maintainer-facing workflow capture is real and reproducible
- governed follow-up recommendations are visible and auditable
- provider quality, utility search quality, and workflow search quality all have regression gates
- the runtime keeps explicit non-automatic boundaries around distill, promote, and evolution apply
- the accepted proof path can be reproduced without changing runtime state

That is enough to support a narrow MVP claim and a release-candidate claim.

## What v0.2 Did Not Solve

v0.2 did not yet make the runtime feel like a daily operator tool. In particular:

- lifecycle visibility is still scattered across trajectories, skill stores, audits, runtime events, and docs
- baseline status is verifiable by rerunning scripts, but not yet surfaced as a normal operator summary
- operators can inspect recommendations, but they still need repo knowledge to understand the current runtime inventory
- dashboard exists, but it is not the right first surface for tightening the daily workflow

So the unresolved gap is not "can the runtime prove one path?" It is "can an operator quickly understand the current runtime state and next safe actions?"

## v0.3 Product Goal

The v0.3 product goal is to move Skill Runtime from a provable MVP into a genuinely usable workflow skill runtime for normal daily operator work.

That means prioritizing:

- lifecycle visibility
- operator comprehension
- explicit safe-next-step guidance
- stable, read-only inspection surfaces
- better continuity between captured work, staging candidates, active skills, and governance status

It does not mean broadening automation boundaries.

## Why Operator Workbench Comes First

Operator Workbench is the right first mainline because it improves product usefulness without changing governance risk.

The first useful problem is simple: an operator should be able to answer, from one command, questions like:

- what trajectories have been captured recently?
- what active skills exist right now?
- what staging candidates exist right now?
- what governed follow-up actions are visible?
- what status is locally available, and what is still missing?
- what can I safely do next?
- what is intentionally not automatic?

This is a better next step than more proof-bundle work because it turns already-proven lifecycle pieces into an actual operator surface.

## First Slice: `operator-summary`

The first v0.3 slice is a read-only CLI summary:

```bash
python -m skill_runtime.cli --root . operator-summary
```

This command should:

- default to JSON
- optionally render human-readable text
- surface runtime-visible state only
- clearly mark missing or unavailable fields
- never execute host operations
- never promote
- never apply an evolution candidate
- never mutate runtime state

## Dashboard Connection Point

This repository already has read-only local and global dashboard surfaces. v0.3 should not restart that work from zero and should not turn this slice into a dashboard rewrite.

The intended direction is:

- `operator-summary` becomes the stable runtime-summary data source
- dashboard and future operator workbench can consume that summary once the contract settles
- page-level UI should stay unchanged until the summary contract is stable enough to depend on

The current minimal connection-point analysis is:

- existing dashboard collection logic already reads local runtime files directly
- `RuntimeService.operator_summary()` now exposes a narrower operator-facing lifecycle summary on top of those same stores
- the lowest-risk future integration is to let dashboard collector read or merge `operator_summary()` output, not to rebuild dashboard pages first

For this slice, the right move is to stabilize the summary contract and keep the dashboard untouched.

## What Still Needs Better Indexing

The current repository does not yet persist every status we might eventually want in one canonical index. In particular:

- provider quality baseline status is only available when a local persisted report exists
- utility search quality baseline status is only available when a local persisted report exists
- workflow search quality baseline status is only available when a local persisted report exists
- operator-level lifecycle summaries still depend on reading several existing stores rather than one purpose-built state index

That is acceptable for the first slice. The product rule is to surface what is real now and mark the rest as missing or unavailable.

## Boundary: Do Not Widen `default-in`

Nothing in this v0.3 direction justifies widening `default-in`.

Operator visibility is useful precisely because it keeps the runtime easier to inspect before more tasks are allowed into the default lane. Better visibility is a prerequisite for future trust, not evidence that broader automatic entry is already warranted.

Current boundary remains:

- no widened `default-in`
- no automatic promote
- no automatic evolution apply
- no pretending expected gaps are solved when they are not
- no converting lifecycle operations into ordinary active skills
