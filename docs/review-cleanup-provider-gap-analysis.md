# Review Cleanup Provider Gap Analysis

Date: 2026-05-05

## Scope

This note compares the two existing review-cleanup provider-quality fixtures only:

- `review_cleanup_provider_quality`
- `review_cleanup_demo_provider_success`

It does not add fixtures, does not change runtime entry policy, and does not treat the positive control as evidence for wider automation.

## Negative Fixture Current Behavior

Fixture: `review_cleanup_provider_quality`

- lifecycle mode: `manual_provider_loop`
- fallback provider: `mock_fallback_provider`
- semantic provider: `mock_semantic_review_provider`
- generated candidate status: `passed`
- audit status: `needs_fix`
- execution smoke status: `skipped`
- terminal loop stage: `audit_failed`

Current interpretation:

- The fixture does not fail because fallback generation crashed.
- It fails because the generated candidate is still template-like and gets blocked by audit before execution is allowed.

## Positive Fixture Current Behavior

Fixture: `review_cleanup_demo_provider_success`

- lifecycle mode: `manual_provider_loop`
- fallback provider: `local_review_cleanup_fallback_provider`
- semantic provider: `local_pass_semantic_review_provider`
- generated candidate status: `passed`
- audit status: `passed`
- execution smoke status: `passed`
- terminal loop stage: `execution_passed`

Current interpretation:

- The positive control passes because the provider generates a concrete, executable workflow that reads review comments, writes a cleanup plan, and optionally writes metadata.
- It is intentionally constrained: it produces a planning artifact and stops short of code edits.

## Why The Negative Fixture Fails Audit

The negative fixture is blocked by both heuristic semantic checks and the mock semantic provider.

Heuristic failures:

- `template-skill`
  The generated skill looks like a template or no-op and does not implement the observed successful trajectory with real runtime operations.
- `artifact-overfit`
  The generated skill hardcodes trajectory artifact names such as `expected_cleanup_plan.md` instead of parameterizing outputs.

Provider-added failures:

- `provider-template-skill`
  The mock semantic provider explicitly flags skills generated by `mock_fallback_provider` as template logic that still needs stronger concrete runtime behavior.
- `provider-weak-runtime-alignment`
  The mock semantic provider flags summary-style output with `steps_executed` but no real `tools.` calls.

The key point is that the negative fixture already has a generated candidate, but that candidate only mirrors inputs, comments, and artifacts from the trajectory. It does not perform the workflow.

## What The Positive Provider Adds

The positive provider closes the gap by adding concrete workflow behavior that the mock fallback does not provide.

Specifically, `examples/providers/review_cleanup_fallback_provider.py` adds:

- real runtime tool calls:
  `tools.read_json`, `tools.write_text`, and optional `tools.write_json`
- explicit required input handling:
  it validates `input_path` and `output_path`
- workflow-specific task logic:
  it reads `review_comments`, separates `must_fix` from non-`must_fix`, and builds a grouped maintainer cleanup plan
- parameterized outputs:
  it writes to `output_path` and optional `metadata_path` instead of hardcoding trajectory artifact names
- a constrained artifact contract:
  the result is a Markdown cleanup plan plus optional metadata, not an attempted code rewrite

This is enough to satisfy the current review-cleanup positive control without relaxing audit.

## What Audit Requires For This Workflow

For this workflow, the current audit path effectively requires all of the following:

- docstring structure with `功能描述`, `输入参数`, and `输出结果`
- real runtime tool usage that overlaps the successful trajectory instead of placeholder comments
- usable kwargs coverage for trajectory-derived inputs such as `input_path`, `output_path`, and `metadata_path`
- parameterized output handling instead of hardcoded artifact names
- no high-severity semantic issue after heuristic checks and provider review are combined

In practice, the biggest gap is not docstring shape. It is the difference between:

- a generated template that describes the workflow
- an executable skill that actually performs the workflow with runtime tools

## Minimal Provider Guidance That Could Reduce The Gap

The smallest useful provider-guidance improvement is not “make mock pass.” It is to push fallback generation closer to executable planning behavior for this workflow family.

Minimal guidance should tell a provider to:

- read structured review input from `input_path`
- write the maintainer plan to `output_path`
- use `metadata_path` only as optional structured output
- separate required fixes from follow-up items
- keep the artifact as a cleanup plan, not source-code edits
- avoid hardcoding demo artifact names from the trajectory
- include real runtime tool calls instead of emitting step comments plus summary fields

That guidance would reduce the gap because it targets the exact audit failures seen in the negative fixture:

- template behavior
- weak runtime alignment
- hardcoded artifact names

This guidance is now wired into the fallback provider request path:

- fallback providers receive a dedicated `provider_guidance` field
- the same guidance is also embedded into the fallback prompt

That improves provider-side context without changing audit thresholds and without forcing the mock negative fixture to pass.

## What Should Not Be Automated

This workflow should still avoid automatic code-edit execution in the provider-quality path.

The provider should not automatically:

- rewrite repository files
- apply code fixes from review comments
- infer merge approval
- decide that all review comments are safe to resolve
- bypass maintainer judgment on ambiguous comments

The current positive control is appropriately narrow because it only generates a grouped cleanup plan.

## Why This Is Not Default-In Evidence

This comparison does not justify widening `default-in`.

Reasons:

- it measures post-task governed-learning fidelity, not runtime entry safety
- the positive case is a controlled provider positive control, not an open-ended maintainer workflow solution
- the negative case still shows that unconstrained fallback output for review cleanup remains audit-blocked
- review cleanup still depends on maintainer judgment even when plan generation can be constrained successfully

This is evidence about provider-quality gap shape, not evidence that review cleanup should auto-enter the runtime lane.
