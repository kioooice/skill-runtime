# v0.2 Core Quality Summary

Date: 2026-05-05

## Purpose

Summarize the v0.2 core quality gates and product boundary so future work can continue from the same map without re-litigating provider quality, utility search, workflow search, or governed follow-up ownership.

This is a documentation summary only. It does not change runtime behavior, query sets, ranking, metadata, active skills, baselines, or `default-in`.

## What v0.2 Now Covers

### Provider Quality Gate

The provider quality gate lives at:

- `scripts/evaluate_provider_quality.py`
- `docs/provider-quality-baseline.json`
- `docs/v0.2-provider-quality-summary.md`

It checks whether provider-generated candidates can move through generation, audit, optional repair, execution smoke, and baseline comparison with expected pass and expected failure cases.

The current baseline includes:

- constrained local provider successes
- fake DeepSeek success and failure controls
- mock template failures
- review-cleanup positive and negative controls
- runtime-service distillation through the provider path

### Utility Search Quality Gate

The utility search quality gate lives at:

- `scripts/evaluate_search_quality.py`
- `docs/search-quality-baseline.json`
- `docs/v0.2-search-quality-summary.md`

It checks fixed local search/reuse behavior for utility and control queries using a temporary runtime root and a small active-skill fixture set.

It covers:

- exact English utility search
- fuzzy English utility search
- structured conversion search
- one maintainer handoff workflow query
- explicit-alias Chinese recall
- English and Chinese negative no-strong-match controls

Utility skills remain useful fixtures and controls. They are not the main product proof.

### Workflow Search Quality Gate

The workflow search gate lives at:

- `scripts/evaluate_workflow_search_quality.py`
- `docs/workflow-search-quality-baseline.json`
- `docs/workflow-search-quality-plan.md`

It evaluates workflow-oriented active fixtures separately from utility controls.

Current expected matches:

- `handoff_continuation -> session_handoff_maintenance`
- `pre_implementation_review -> pre_implementation_workflow_review`

Current expected gaps:

- `maintainer_review_cleanup`
- `governed_learning_follow_up`

Current negative workflow control:

- utility merge requests should not recommend workflow skills in the workflow-only fixture set

### Workflow Expected-Gap Decision

The expected-gap decision lives at:

- `docs/workflow-gap-active-skill-decision.md`

Current decisions:

- `maintainer_review_cleanup`: needs more evidence before becoming an active workflow-search skill
- `governed_learning_follow_up`: keep as host follow-up, not active workflow search

Those gaps are intentional. They are not hidden failures and should not be patched with ranking changes.

## What Has Been Proven

### Provider-Generated Candidates Can Be Evaluated

The provider loop can now report whether generated candidates:

- were generated successfully
- passed or failed audit
- attempted repair when expected
- passed execution smoke when expected
- matched the machine-readable baseline

Expected failures are first-class quality signals, not accidental red output.

### Workflow And Schema Fidelity Issues Can Be Detected And Fixed

The v0.2 provider work found and closed concrete fidelity problems:

- deterministic copy rules were too broad for copy-plus-sidecar workflows
- fallback-generated metadata could drift from candidate kwargs
- provider output could be template-like even when generation succeeded
- review-cleanup fallback output needs executable workflow behavior, not summary-only code

The current provider baseline can preserve those distinctions.

### Search And Reuse Behavior Can Be Regression-Checked

The utility search baseline makes local search behavior reproducible:

- positive queries can be checked for the expected recommended skill
- negative queries can check that no strong recommendation is made
- alias-driven recall can be tracked without claiming broad semantic retrieval
- baseline comparison can catch regressions, unexpected failures, unexpected passes, missing queries, and extra queries

### Workflow Search Can Honestly Distinguish Active Matches From Expected Gaps

The workflow search baseline shows two different states:

- active workflow matches that should recommend a skill
- expected gaps where no active workflow skill should currently own the intent

That distinction matters because not every valuable maintainer workflow should become an active search skill immediately.

## What Has Not Been Proven

v0.2 has not proven:

- broad semantic retrieval
- general multilingual understanding
- arbitrary maintainer workflow automation
- arbitrary provider generation quality
- review cleanup as an active workflow skill
- governed learning follow-up as an ordinary search skill
- silent promotion or automatic evolution of skills
- wider `default-in`

In particular:

- `maintainer_review_cleanup` is currently demo plus provider positive-control evidence, not an approved active workflow-search skill.
- `governed_learning_follow_up` is currently host lifecycle operation evidence, not active skill evidence.

## Current Product Boundary

### Utility Skills Are Fixtures And Control Group

Utility skills are still valuable for:

- deterministic smoke coverage
- local execution checks
- search-quality controls
- false-neighbor diagnostics

They should not be treated as the main maintainer-value story.

### Workflow Skills Are Main Product Value

The product thesis is workflow governance for maintainers:

- session handoff continuation
- pre-implementation direction review
- runtime gate and verification routing
- deployment, repo-impact, reporting, and stage workflows

Workflow search should stay focused on these maintainer workflows.

### Lifecycle Operations Remain Host Follow-Up

Lifecycle operations such as:

- `distill_trajectory`
- `audit_skill`
- `promote_skill`
- `review_evolution_candidate`
- `apply_evolution_candidate`
- `rollback_evolution_candidate`

should remain explicit host operations surfaced through `recommended_host_operation`.

They should not be wrapped as ordinary active workflow-search skills just to satisfy search queries.

### Expected Gaps Are Intentional Until Evidence Changes

The current workflow expected gaps should remain:

- `maintainer_review_cleanup`
- `governed_learning_follow_up`

`maintainer_review_cleanup` can become an active workflow-search skill later only if a narrow cleanup-plan boundary is approved.

`governed_learning_follow_up` should stay host-follow-up unless the product model changes. The current evidence supports clearer host presentation, not active metadata.

## Recommended Next Core Slice

The narrow host presentation helper slice now exists.

Current presentation-layer artifacts:

- `skill_runtime/presentation/recommendation.py`
- `scripts/demo_recommendation_presentation.py`
- `scripts/render_recommendation_presentation.py`
- `docs/host-recommendation-presentation-summary.md`

What that slice proved:

- governed follow-up payloads can be rendered consistently as card/text output
- hosts can inspect fixture scenarios without re-implementing wording
- operators can render a real payload JSON file without calling runtime or executing an operation

What it did not become:

- not a dashboard feature set
- not automatic execution
- not a runtime decision change
- not active-skill search coverage

Recommended next slice: real host integration dogfood / operator validation.

Reason:

- `governed_learning_follow_up` should not become an active workflow skill.
- the presentation layer now exists, so the main open question is practical host/operator usability
- the next useful work is validating real consumption of the current contract, not expanding presentation code further

Scope for that slice should stay narrow:

- validate real host/operator use of current recommendation payloads
- confirm whether formatter text, card output, and renderer CLI are sufficient in actual operator flow
- keep confirmation and governance boundaries visible

Non-goals for that slice:

- no automatic promotion
- no automatic apply
- no active-skill wrapper for lifecycle tools
- no workflow baseline query expansion by default
- no `default-in` expansion

## Default-In Boundary

No evidence in the v0.2 core quality work supports widening `default-in`.

Provider quality gates measure post-task governed-learning fidelity. Search quality gates measure retrieval and reuse behavior. Workflow search expected gaps measure product coverage boundaries. None of these prove that broader task families should automatically enter the runtime lane.
