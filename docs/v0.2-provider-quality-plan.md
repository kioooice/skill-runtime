# v0.2 Provider Quality Plan

Date: 2026-05-05

## Goal

Build a small, honest provider-quality evaluation loop for Skill Runtime that measures whether provider-backed governed learning is producing candidates that can survive generation, audit, optional repair, and basic execution smoke checks.

The immediate deliverable is not a new runtime feature. It is a repeatable local evaluation entrypoint that makes provider quality visible.

## Why This Is The Next Core Function

`v0.1.0-alpha` proved that the project has a credible public shape, a maintainer-facing demo, and conservative workflow boundaries.

The next core question is whether provider-backed governed learning is actually good enough to trust as a serious path for candidate generation and review.

That is the right next function because:

- fallback generation is the path taken when deterministic rules do not match
- semantic review is the last quality gate before promotion is even considered
- provider quality currently affects whether governed learning produces useful candidates or template noise
- the project needs evidence about provider quality before it needs broader automation

## Current Provider Limitations

The current provider path has real limits:

- fallback distillation is provider-backed, but mock-backed by default
- semantic audit is provider-backed, but mock-backed by default
- existing tests mostly validate contracts, quality gates, and repair behavior in isolation
- the live DeepSeek smoke covers one end-to-end path, but it requires a real API key
- there is no single local evaluation script that reports fixture-by-fixture loop outcomes honestly

That means the repo can prove contract correctness more easily than it can prove provider-quality outcomes.

## Evaluation Fixtures

`v0.2-provider-quality` should start with a small fixed fixture set that can run locally without a real API key.

Initial fixture types:

1. A demo-provider success case using the local copy-metadata fallback provider plus the local pass semantic review provider.
2. A mock-provider audit-pressure case using the default mock fallback provider plus the default mock semantic provider.
3. A fake DeepSeek repair case using scripted or fake responses that force one bad candidate and one repaired candidate.
4. A fake DeepSeek failure case where generation or semantic review fails and the report must surface the reason directly.

These fixtures should be enough to measure:

- candidate generation shape
- audit outcome
- repair attempt visibility
- execution smoke viability
- follow-up recommendation visibility

## Generate -> Audit -> Repair -> Execute Loop

The loop to measure is:

1. Select one evaluation fixture and provider configuration.
2. Generate a staging candidate from an unmatched or forced-fallback trajectory.
3. Audit the generated candidate with static plus provider-backed semantic review.
4. If the fallback provider itself supports one repair attempt, record whether repair was attempted.
5. If the candidate passes the audit, run an execution smoke check with concrete inputs.
6. Report the final outcome without hiding failure.

The evaluation report must show whether the loop stopped at:

- generation failure
- audit failure
- repair exhaustion
- execution smoke failure
- successful candidate execution

## Success Criteria

`v0.2-provider-quality` is successful if:

- there is a single local evaluation script for provider quality
- it runs with no real API key by using mock or demo providers
- each fixture produces a structured result line or record
- the result includes generation status, audit status, repair attempted or not, execution smoke status, failure reason, and `recommended_next_action` when available
- failures remain visible instead of being normalized into fake success

## Failure Criteria

This work fails if:

- the evaluation path only works with a real provider API key
- the report hides generation or audit failures
- repair attempts are invisible
- execution smoke is skipped without being reported as skipped
- the script implies that a candidate is promotion-ready when the audit failed
- the evaluation work changes runtime entry policy or promotion behavior

## What Will Not Be Changed

This `v0.2` slice will not change:

- dashboard behavior or presentation
- `default-in` scope or runtime entry policy
- automatic promotion behavior
- automatic application of evolution candidates
- maintainer-facing public release positioning

This is a provider-quality measurement pass, not a product-boundary expansion.

## Why Default-In Remains Unchanged

Provider quality is about governed learning quality after normal task completion, not about making more tasks auto-enter the runtime lane.

Even perfect provider results would not by themselves justify widening `default-in`, because:

- runtime entry policy is about workflow boundary and task risk
- review cleanup and other open-ended maintainer judgment tasks still need conservative handling
- the current evidence set still does not show that broader automatic entry improves outcomes

There is still no evidence supporting expansion of `default-in`, and this `v0.2-provider-quality` work is not intended to create that evidence indirectly.
