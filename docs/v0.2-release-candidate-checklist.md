## Known Non-Blocking Gaps

- semantic audit is still mock-backed by default unless an external provider is configured
- fallback distillation is still mock-backed by default unless an external provider is configured
- utility and workflow retrieval remain lexical/local, not embedding-based
- Chinese retrieval remains explicit-alias-driven, not general multilingual understanding
- `maintainer_review_cleanup` remains a demo plus proof-path slice, not an approved active workflow-search skill
- governed learning follow-up remains a host follow-up operation, not an active workflow-search skill
- dashboard exists, but it is not the release proof surface for v0.2
- public traction remains limited and should not be overstated

## Blocking Gaps

None for the current `v0.2.0rc1` release-candidate gate.

## Release Risks

- readers can still overread the project as broader workflow automation than current evidence supports
- provider-backed quality is only strongly proven on the fixed local fixture set
- search quality is reproducible, but still intentionally narrow and metadata-driven
- expected workflow gaps could be misread as failures if release notes do not keep the product boundary explicit

## What Should Not Change Before v0.2

Do not change before the v0.2 release cut unless a real regression forces it:

- search ranking
- workflow search query set
- `default-in` boundary
- service recommendation decision logic
- auto-promote behavior
- auto-apply evolution-candidate behavior
- CLI recommendation scope beyond the accepted `capture-trajectory` path
- dashboard scope
- active-skill ownership of `maintainer_review_cleanup`
- host-follow-up ownership of governed learning follow-up

## Why This Does Not Justify Widening Default-In

The current evidence proves:

- one governed maintainer proof path is externally reproducible
- provider quality can be regression-checked on a fixed fixture set
- utility search quality can be regression-checked on a fixed fixture set
- workflow search can distinguish active matches from intentional expected gaps

It does not prove:

- broader runtime-entry safety
- broader workflow automation safety
- broader autonomous follow-up safety
- broader maintainer workflow coverage

Therefore this RC does not justify widening `default-in`, and there is currently no evidence supporting such a change.
