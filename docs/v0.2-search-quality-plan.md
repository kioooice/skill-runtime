# v0.2 Search Quality Plan

Date: 2026-05-05

## Goal

Establish a local, reproducible search-quality baseline for skill search and reuse before changing retrieval behavior.

The immediate target is not a better algorithm. The immediate target is an honest local report that shows:

- which fixed queries currently retrieve the expected skill
- which queries only produce weak results
- which queries do not retrieve a usable match at all

## Why Search Quality Is The Next Core Slice

Provider quality now has a local evaluation entrypoint, a machine-readable baseline, and a stable regression gate candidate.

Search and reuse are the next core slice because they sit earlier in the maintainer workflow:

- if search quality is weak, reuse quality becomes accidental
- if reuse recommendations are hard to reproduce locally, search behavior becomes a black box
- if retrieval drift is invisible, it is hard to judge whether later reuse policy changes are justified

Search quality therefore needs the same first move that provider quality needed:
measure the current local behavior before trying to redesign it.

## Current Search Limitations

Current retrieval is local and lexical. That keeps it explainable, but it also imposes visible limits:

- tokenization only keeps ASCII-style alphanumeric tokens and underscores
- no embedding, vector, or external semantic retrieval is used
- ranking is driven by lexical overlap plus metadata boosts:
  summary overlap, schema overlap, tags, provenance, usage, audit score, and active-status bias
- recommendation is thresholded:
  a result may appear in the list but still not be recommended for execution if the score stays below the strong-match threshold
- weak multilingual coverage is expected, especially for Chinese-only queries

The first baseline should record these limits rather than hide them.

## Proposed Local Fixtures

Use a temporary runtime root and import a small subset of existing active skills into it.

Initial fixture set:

- `merge_text_files`
- `json_to_csv_dogfood`
- `session_handoff_maintenance`
- `pre_implementation_workflow_review`
- `directory_text_cleanup_dogfood`

Why this subset:

- it covers stable utility reuse
- it covers structured conversion
- it covers maintainer workflow routing
- it stays small enough to keep the baseline understandable

## Expected Positive Queries

The first baseline should include at least these positive-intent queries:

- exact English query:
  `merge txt files into markdown`
- fuzzy English query:
  `combine text files into one markdown document`
- structured conversion query:
  `convert json records to csv`
- maintainer workflow query:
  `resume handoff update tasks decisions`

These queries should ideally produce the expected skill as the recommended top result.

## Expected Negative Queries

The first baseline should also include at least one negative query that should not strongly match anything:

- `send an email newsletter campaign`

This query may still produce low-score lexical noise, but it should not become a strong recommended reuse.

## Ranking Expectations

Initial ranking expectations should stay narrow:

- exact and fuzzy positive queries should place the expected skill at top-1 when current retrieval is working well
- the maintainer workflow query should recommend the intended workflow skill rather than an unrelated utility
- the negative query should not produce a recommended skill
- a Chinese query can be included as a known-limitation probe; if it fails, the report should say so honestly rather than treating it as a fake pass

## Baseline Comparison Idea

After the first local report exists, the next step can mirror provider quality:

- add a machine-readable search-quality baseline JSON
- compare current query outcomes against the stored baseline
- separate:
  - matched cases
  - regressions
  - improvements
  - known weak or negative cases

That comparison layer is a later step.
The first step is a stable local evaluator and a fixed query set.

## What Will Not Change

This slice does not change:

- the retrieval algorithm
- dashboard scope
- `default-in` policy
- automatic promotion
- automatic application of evolution candidates
- audit policy
- embeddings or any external search service

## Why This Does Not Justify Widening Default-In

Search quality is a retrieval and reuse-quality question, not a runtime-entry safety decision.

Even if search quality improves, that still does not answer:

- whether a task should enter the runtime lane automatically
- whether maintainer judgment tasks are safe for wider automatic entry
- whether reuse should be silent, suggested, or skipped

There is still no basis here for widening `default-in`.
